## 1. 已确定的产品边界

用户已确认：任务与会话统一为一套；专家可选，不选使用通用助手；专家保留独立记忆、人设、能力配置；工作目录跟随项目。

这一决定替换原约定中“Task 不关联专家”的部分，新的关系是：Task 可选择已有专家，项目始终独立。创建项目、任务或通用助手会话均不创建专家。

| 对象 | 持有内容 | 生命周期 |
| --- | --- | --- |
| 专家 | 稳定身份、人设、专业指令、默认模型、能力、长期记忆 | 跨任务持续存在 |
| 项目 | 服务端目录、客户端目录、项目规则与能力引用 | 跨任务持续存在 |
| Task（统一工作记录） | 多轮消息、所选专家、可选项目、附件、审批、成果、归档与来源关系 | 可持续追问 |
| Turn（一次执行） | 请求、实际专家、配置快照、上下文、检查点、执行与交互状态 | 一轮独立受理与恢复 |
| 运行智能体 | 依据 Turn 快照构造的执行实例 | 按执行需要创建、释放 |

对用户，统一入口继续使用“项目和任务”，详情呈现为多轮会话。普通问答到复杂工作均留在原 Task，无须进行“会话转任务”。当前轮完成与整条记录归档分别处理。

首期配置规则：空闲且无待发队列时可换专家，从下一轮生效；首轮发送后固定项目。需要更换项目时创建关联分支，明确携带哪些上下文，不自动移动文件。

## 4. 数据模型与版本

继续使用 `project_tasks`、`project_task_turns`；保留现有公开 `task_id`、`turn_id`。建议增量如下，确切 DDL 在 D1–D3 契约阶段定稿。

| 位置 | 建议增加或调整 | 约束 |
| --- | --- | --- |
| `project_tasks` | `selected_expert_id` 可空、`action_mode`、置顶字段、独立 `configuration_revision` | 专家引用指向 `agents.agent_id`；空值为通用助手；选择修订与输出的 `list_revision` 分开 |
| `project_task_turns` | 可查询的实际专家引用；扩展 `configuration_json` | 每轮保留真实执行身份及不可变有效配置 |
| `agents` | 独立 `config_revision` | 配置变更递增，运行状态更新不递增 |
| Task 配置事件 | 追加专家切换等事件，含事件 ID、前后引用、生效位置 | 与 Task 更新同事务；历史回复不改身份 |
| Task 来源关系 | 原 Task／Turn 或旧 thread、来源锚点、操作类型与幂等键 | 支持分叉、编辑分支、旧会话续接；不是双向同步表 |
| 记忆写入工作项 | 来源 Turn、作用域、内容摘要、状态、幂等键与投递收据 | 与控制面终态事务联动；目标存储去重能力需验证 |

注意旧 `config_json.expert_id` 可能表示模板名，`published_expert_id` 表示发布资源；二者均不能替代持久专家的 `agent_id`。新字段统一命名为 `selected_expert_id` 并在 OpenAPI 明确其身份类型。

专家有效配置版本由 `config_revision + profile_digest` 表示。`profile_digest` 包含实际参与执行的人设、方法文件和能力内容摘要；仅递增数据库版本无法覆盖外部文件修改。由服务端读取并固化快照，后续执行不重新解释已受理轮次。

用户级列表建立与筛选一致的分页索引和 owner 全局同步范围；游标绑定 owner、筛选条件和稳定排序。旧项目范围与无项目范围的语义不改成含混的“全部”。

SQLite/PostgreSQL 维护成对迁移、等价约束和幂等补齐。实施时核对已发布版本、实际数据库 watermark 和当前未发布迁移，决定折叠或新增编号；本规划不预先指定下一个迁移号。

## 5. 配置解析与执行流程

拟新增一个无启动副作用的专家配置读取模块，以及 Task 有效执行配置解析模块。通过 `SharedServices` 与领域服务取资源，不让 API 路由承担规则，不从路由直接调用数据库 Repo。

解析流程：

1. 从认证信息取得 owner，校验 Task、项目及专家的访问权限；不能信任请求中的 owner。
2. 读取当前项目配置、所选专家的有效人设／能力及版本。专家文件内容通过 `BackendWorkspace` 访问。
3. 解析本轮覆盖、模型／路由与资源，确认目录和引用实际可用。
4. 固化项目版本、专家版本与内容摘要、模型、能力、记忆访问范围、工作目录和资源快照。
5. 在事务内再次核对配置与 Task 修订，幂等保存请求和 Turn 后入队。模型分类与远程准备放在事务外。
6. worker 根据快照构造运行实例，恢复 Task 自己的上下文与检查点，独立挂接专家记忆访问。
7. 执行过程沿用现有控制面记录计划、工具、审批、暂停、产物和实际用量。
8. 持久保存结果，再按专家既有记忆策略处理记忆工作项；原请求重传不再次执行工具或重复采集。

当前未提交的 `task_submission.py` 已在路由分类前后核对 digest；新专家配置及内容摘要必须纳入该 digest，避免分类期间换专家配置却使用旧决策。

| 配置 | 确定规则 |
| --- | --- |
| 工作目录 | 当前项目目录；未配置时使用 Task 独立持久空间 |
| 专家人设 | 所选专家的有效配置；未选择时使用通用助手指令 |
| 项目规则 | 与专家人设分别注入，保留来源；不覆盖系统权限规则 |
| 模型 | 本轮明确模型／路由优先，其次专家默认，再用当前用户／系统默认；不可用时明确报错 |
| 默认能力 | 合并专家与项目启用资源，按稳定资源 ID 去重；同名不同内容冲突明确报错 |
| 本轮能力覆盖 | 省略表示继承有效默认集合；显式列表完整替换；`[]` 表示本轮禁用该类可选资源 |
| 权限与审批 | 当前用户、资源授权和审批策略的共同约束，不能由专家提示词扩大 |
| 专家变更 | 下一轮读取新配置；恢复原轮时保持原快照，并重新确认现时权限 |

恢复原轮不重新选择专家、不重新路由、不重新召回不同的记忆文本。配置快照不保存密钥；凭据在执行时按当前授权解析，授权撤销优先于旧快照。

项目 ID 固定不代表目录永远不变。项目配置更新后，新受理轮次使用新版本；如果解析出的目录改变，页面显示新旧目录并要求用户重新确认执行范围。客户端本地队列中尚未被服务端受理的消息，在提交时返回版本冲突，不静默改目录执行。已经返回 `202`、已有 Turn 的服务端 `queued` 轮次和活动轮次继续原目录快照并检查当前授权；项目后来更新不把原受理请求变成配置冲突，不自动搬迁工作文件。

行动模式使用独立 `action_mode=ask|plan|craft`，持久保存默认值并固化到每轮快照；默认沿用现有 Task 的执行语义 `craft`。`ask` 允许配置范围内的回答、结构化只读与检索，禁止外部写操作及任意 shell；`plan` 允许同类读取与形成计划，外部执行必须由后续 `craft` 轮次发起；`craft` 按能力与审批执行。限制作用于根智能体、子代理及客户端工具，不能只改变前端按钮或提示词。内部历史、计划和经授权的记忆采集按各自策略持久保存，不作为外部操作工具。

资源快照与执行代码版本分别记录。现有 Skill 快照不等于插件代码／中间件已被完整保存；应记录依赖与插件内容摘要，恢复时检查不兼容变化。无法恢复原执行环境时明确中断，不声称原轮配置已完全重现。

## 6. 专家记忆：独立位置、范围与检查点

这是关键路径，不能只修改一个 `memory_namespace`。

现有专家记忆默认路径跟专家 workspace 相关；现有 Harness 的 Memory 还可能承载检查点。直接把 Task Memory 替换成专家 Memory，会把不同任务的恢复状态也带到专家存储。实现必须同时做到：

- 工作文件使用项目／Task 工作空间。
- 人设与能力源文件使用专家自己的系统存储。
- 专家长期记忆使用稳定的独立存储描述。
- Task 上下文、检查点、附件和执行日志始终归 Task／Turn。

建议由 Octop 领域层统一记忆访问，显式设置 Task checkpointer，专家记忆只提供召回、读取、写入和维护能力。专家配置不要求先启动一个常驻执行实例才能被 Task 使用。

推荐的作用域：

| 范围 | 隔离标识 | 召回与写入规则 |
| --- | --- | --- |
| 专家通用记忆 | owner + expert | 一般偏好、专业方法等可跨项目复用的事实 |
| 专家项目记忆 | owner + expert + project | 项目事实只在当前项目召回；默认采集不直接提升为通用记忆 |
| 专家无项目任务记忆 | owner + expert + task | 无项目工作事实留在当前任务范围，明确提炼后才进入专家通用记忆 |
| 当前任务上下文 | owner + task | 对话、工具结果、压缩与检查点；不自动等同长期记忆 |

共享专家配置不意味着共享用户记忆。同一 Task 中换专家后，当前记录上下文继续可见；新专家只连接自己的记忆库，旧专家记忆不被搬入新专家库。

未选择专家时不创建隐含专家，也不增加跨任务的用户通用记忆库；沿用当前 Task 自己的记忆与上下文。项目／本轮既有 `memory_enabled` 控制 Task 记忆，本轮设置优先于项目默认；另以 `expert_memory_enabled` 控制是否连接当前专家的长期记忆，省略时遵循专家策略。专家自身关闭记忆时，本轮不能强行打开；本轮显式关闭专家记忆则同时关闭召回与采集。关闭长期记忆不删除消息、检查点或既有记忆，自动采集与提炼继续遵循专家的既有授权策略。

本地安装的 `octop-memory 1.0.0`、`octop-harness 1.0.1` 已核对：公开 recall 主要按 query/limit 工作，metadata 不能直接作为 owner/project 授权过滤；session/thread 标签也不构成隔离。SQLite 通过 namespace 前缀表隔离，PostgreSQL 通过 namespace 列隔离；由 Octop 服务端严格控制可访问的 namespace，所有工具读写都经过作用域检查。namespace 使用稳定哈希编码，避免规范化后的名称碰撞。PostgreSQL 记忆 backend 当前使用单连接及共享事务状态，不能直接当成线程安全连接池并发使用。

Harness 当前单个 MemoryService 的挂接方式不能直接满足“通用记忆 + 项目记忆”双范围，需 Octop 适配层，并拦截所有记忆工具的按 ID 读取与写路由。验证不通过时不能绕回一个无范围的共享记忆库。

并发与采集设计：同一记忆范围的写入／抽取串行协调，模型执行仍可跨 Task 并行；控制面持久记录待采集来源与进度。必须核对目标记忆存储是否支持确定来源 ID 的幂等写入；控制面 outbox 本身不能提供跨库 exactly-once。写入结果未知时保留待核对状态，不盲目重放。若依赖缺少所需原子去重接口，列为依赖扩展任务，不能修改安装目录后当作已交付。

旧记忆缺少项目来源，无法自动恢复隔离。原库和原路径保持可访问；新流程提供明确的旧记忆接入方式，用户选择使用既有未分域记忆或整理为新范围。不能自动把所有旧记忆声明为“通用记忆”。这项策略在 D1–D3 定稿并影响最终验收。

### 6.1 本轮 M3 记忆实现与边界

`expert_memory.py` 负责范围、冻结召回和原始采集，`expert_memory_extraction.py` 负责后台抽取与晋升，`expert_memory_management.py` 提供查询、人工保存和策略维护。自有专家继续复用原记忆 backend，但新 general/scope 与显式只读 legacy 分开；共享专家的非所有者使用当前 Task owner 的独立 SQLite 文件和 namespace，不连接发布者的记忆 backend、凭据或 legacy。团队宿主和每个成员各用自己的专家身份；成员委派证据按真实 Turn 汇总，完成后进入 scope，不伪装成人类消息晋升 general。

原始采集在写库前提交确定来源的 `expert_memory_jobs` 工作项，采集 journal 确认后，由独立 worker 仅处理已完成且未取消的 Turn。每个进程至多进行一个抽取请求，原始证据按本轮固定 ID 读取，不反复扫描整个 Task。抽取调用复用配置中的可用 `memory.aux_model`，否则使用已受理 Turn 的实际模型；非所有者使用共享专家时不读取发布者的辅助模型。调用经过原有用户额度检查、usage 与 model-call 账本，单请求设有时间、输入和输出上限。

核对发现 `MemoryService.extract(..., incremental=True)` 的游标仅在内存，重建实例会重复抽取。本轮使用无写入副作用的 `CandidateExtractor`，先持久保存候选结果，再通过 `PromotionWorker` 的证据、去重和冲突规则写入当前 scope。general 只接受高置信的用户 Preference：必须保留可核对的完整原句，明确包含“跨项目／所有项目／任何项目／通用偏好”等范围，整条来源不能带项目、路径或临时限定；截断来源、助手回复和团队委派均不能自动晋升。general 仅复制这条原句证据，保留来源 namespace、Task、Turn、candidate 及规则版本，不复制项目整段 transcript。其他事实留在 scope，用户仍可通过显式人工保存维护 general。

工作项记录 `queued → extracting → ready → applying → done` 阶段。已保存候选可在进程恢复后继续；每个目标 namespace 内的写入与完成收据处于同一记忆事务，控制面确认丢失时先核对收据，不重复生成 atom。模型结果未持久确认或写入结果待核对时保留 `uncertain`，不自动重放；没有把控制面 outbox 宣称为跨库 exactly-once。采集、召回及晋升都重新检查当前身份与策略，写入使用范围锁和用户／专家／Turn 权限锁，停用、取消、权限撤销优先于旧快照；正常停服保留已知候选供下次继续。

记忆面板的策略响应包含 `auto_extract_enabled`、`general_promotion_enabled`、`policy_editable`，查询响应包含当前 Task／专家的工作项状态。本人可维护自己的共享专家或团队策略；共享使用者不能修改发布者的全局策略，也不能启用其 legacy。旧记忆不自动重新分类，本轮不自动生成 library 的 episode/page，也不强制接纳冲突或低质量候选。SQLite 及恢复边界已定向验证，真实 GLM-5 已验证自动抽取、持久化与新 Task 召回；PostgreSQL 实机、跨平台锁行为和其他供应商仍按发布候选验收执行。

## 7. 调度、并发与恢复

以现有持久队列、租约和 Task 单活动轮次约束为基础，增加跨 Task 有界并发调度；不引入外部队列服务。

- 同一 Task 同时最多一个活动 Turn；幂等请求不能抢出第二个执行。
- 多个 Task 可同时推进，长任务、等待审批或等待客户端工具不阻塞所有其他对话。
- 内部执行并发上限与模型调用限额分别控制；复用现有运行限制，新增配置项须有实际需要。
- 每个活动 Turn 独立持有任务、取消信号、租约和检查点；重启只恢复符合条件的工作。
- 等待态与运行态分别记账；不能简单释放所有对象导致审批回来无处续接，也不能无界保留执行实例。
- 记忆维护协调器同时约束旧专家与新 Task 的记忆写入，避免两条路径各自持锁却共同写库。

M1 的必要验收是“一条长工作和另一条普通问答能独立推进”，而不是只证明四种创建组合能成功。

## 8. API、事件和前端状态

沿用 `/api/projects` 与 `/api/project-tasks`。下面为拟定契约方向，不表示端点均已实现：

| 接口 | 变更或补充 |
| --- | --- |
| `POST /api/project-tasks` | 可选 `project_id`、`selected_expert_id`；省略专家为通用助手 |
| `GET /api/project-tasks` | 显式 scope 区分 all／standalone／project，支持专家、状态、归档、标题查询及置顶排序 |
| `PATCH /api/project-tasks/{task_id}` | 专家选择、行动模式与置顶等设置；配置变更带 expected configuration revision，忙碌时返回类型化冲突 |
| `POST .../{task_id}/messages` 及 retry | 携带 `expected_configuration_revision` 与 `expected_project_revision`，受理时冻结实际身份、行动模式与配置；请求 ID 重传复用原 Turn |
| `GET /api/project-tasks/resources` | 返回可选择专家、模型、资源与支持能力，不返回凭据 |
| `POST .../{task_id}/forks` | 从完成边界创建分支；指定锚点与目标范围；复制上下文，不复制活动执行和授权 |
| 编辑／重新生成动作 | 复用分支服务并明确来源，和失败／取消后的 retry 区分 |
| 显式旧会话续接接口 | owner 校验、来源快照、目标专家／项目、幂等键；一次接入，不持续同步 |
| 既有 memory API | 领域层统一解析专家存储与访问范围；保留 owner 校验及维护互斥 |

本轮不新增 AgentComputer 专用协议和远程项目／任务 Bridge。

P0 需核对既有客户端对新增受理字段的消费方式，不能假设扩展字段成为必填项后旧客户端仍可正常使用。保持 AgentComputer Swift/UI 本轮不改；若严格版本契约需要消费者同时升级，必须列出明确的发布依赖与额外工作，不通过静默忽略版本校验绕过，也不声称已验证兼容。

`expected_configuration_revision` 是独立的选择配置版本，不能复用随输出变化的列表版本。创建、messages、retry 及相应 WS 命令均明确字段语义，版本纳入幂等指纹并在最终受理事务校验；重传原请求仍返回原 Turn，不因后来的配置更新而重新执行。无项目时 `expected_project_revision=null`，有项目时核对实际项目版本；空闲换专家或行动模式递增配置版本。仅客户端存在的待发队列不可能由服务端全局获知，因此跨标签页竞争依靠受理时的版本检查阻止错误执行。

WebSocket／事件快照新增所选专家、每轮实际专家、配置事件、来源及必要 revision；保留既有内容、交互、列表版本分离。更新 `docs/project-task-websocket.md` 与 schema，并验证重连后配置事件不重复、旧状态不覆盖新状态。

前端使用 Task ID 作为详情和 store 的稳定身份。建议唯一详情路由 `/conversations/:taskID`，管理入口继续“项目和任务”；不能占用现有 `/tasks`，它当前属于自动化页面。

新建草稿有独立 draft ID，发送后绑定 Task；草稿、附件与发送队列不再以专家 ID 为主键。换专家不清空草稿。排队消息固定受理意图，运行／审批／本地队列未清空时禁止换专家；服务端不假定能看到另一个浏览器的未发送内存队列，客户端需同时携带并校验选择修订。

现有两套待发队列都是内存队列，本计划不宣称刷新后保留未发送消息；若增加持久草稿，优先保存文字与选择，不把尚未授权的文件或请求自动上传、执行。

## 10. 旧数据、删除与外围调用

旧 `agents`、目录、记忆库、`threads`、正式消息归档和检查点完整保留。新专家设置页移除“工作目录”职责，并不删除旧专家目录；它可能仍承载历史数据和配置源文件。

旧会话续接由用户明确操作：先读取 owner 可访问的来源快照，形成带来源的 Task 上下文，记录稳定来源映射，之后只向新 Task 写入。旧工具内容作为历史事实展示，不伪造新的工具成功回执；未完成工具调用不能直接进入新运行状态。附件逐项校验，有缺失则明确显示；旧审批、凭据与工具权限不转移。

已有 `conversation_imports` 可参考其来源与幂等思路，但它面向外部导入且允许部分来源更新，不直接拿来实现旧 thread 的持续双向同步。

建议统一后采用以下删除策略：

- 有历史引用的专家优先停用；引用存在时禁止直接物理删除，不能级联删除 Task。历史显示快照，后续执行须显式选择可用专家或通用助手。
- 归档项目保留全部历史，仍须先停止活动任务。用户明确删除项目时，服务端自动停止并确认活动轮次退出，再原子删除项目及其中全部 Task、历史附件和相关记录；停止未确认则保留数据并允许重试，不要求用户逐个删除 Task。
- 归档 Task 不删除专家记忆；删除 Task 也不能直接清空共享的专家记忆。记忆来源失效的展示、遗忘与数据清理另有明确动作。
- 所有物理删除、批量迁移和清库都需要独立明确授权，不包含在本规划的实施默认动作内。

resident 委派当前调用普通 Task 服务，需验证新增专家缺省行为不变；不能把私人管家的固定身份或专用授权误暴露为普通专家选择。旧 IM、CLI、cron 依赖 AgentManager 和 threads，保留现有调用，新增适配另列。不要在本轮提前删除 AgentManager、thread 服务或旧路由。

## 13. 验收与验证策略

每阶段只跑与变更直接相关的验证；最终候选版本再执行仓库要求的完整门禁，不在本规划阶段运行。

| 验收组 | 必须证明的行为 |
| --- | --- |
| 四种组合 | 有／无项目 × 有／无专家均可创建、追问、归档；Task ID 稳定 |
| 目录 | 专家跨项目工作仍使用当前项目目录；无目录使用 Task 空间；客户端路径不被服务端探测；本地待发队列检测项目变更，已受理 Turn 保持原快照 |
| 身份与记忆 | 专家 A／B、用户 A／B、项目 A／B 隔离；同专家可复用通用记忆；旧未分域记忆不被自动重新分类 |
| 检查点 | 同一专家的多个 Task 不共用恢复状态；恢复不重新召回、换模型或重复调用已完成工具 |
| 并发 | 长任务不阻塞另一普通会话；等待审批／客户端时可推进其他工作；同 Task 不双跑 |
| 幂等 | 相同请求重传不新建 Turn；不同配置重用请求 ID 返回冲突；记忆写入不因重启无依据重复 |
| 配置竞争 | 模型分类、专家切换、项目更新与提交竞争时能检测版本；排队／恢复使用确定配置 |
| 消息与交互 | 工具／计划／审批／提问可刷新恢复，交互回复继续原 Turn；实际失败不显示完成 |
| 行动模式 | ask／plan 在服务端及子代理／客户端边界阻止外部执行；craft 仍需审批；模式与推理强度分别生效 |
| 分支 | 编辑／fork／再生成保留原记录与执行事实；不克隆授权、租约和活动队列 |
| 文件与工具 | 附件、产物、终端、浏览器、工具 UI 均按当前 Task／owner 校验，旧专家目录不隐式授权 |
| 生命周期 | 归档保留历史；明确删除项目须确认停止后清理全部 Task，停止未确认不部分删除；目录文件、专家记忆及项目外分支保留，停用专家不静默切通用助手执行 |
| 旧能力 | 旧链接准确可读；resident、IM／CLI／cron、共享／团队现有路径不被提前破坏 |
| 平台与数据库 | SQLite／PostgreSQL等价；Linux／Windows路径、锁与迁移验证遵循仓库惯例 |

实施阶段建议运行相应 `uv run pytest` 的 DB、projects、agents/memory、API／integration 用例；前端运行涉及 store／队列／交互的现有测试、`npx tsc -b` 及必要 lint。API 更新需检查 `/api/docs` 的 summary/schema，更新中英文错误码与 i18n 校验。UI 最终按仓库规则构建，不手改 `src/octop/dashboard/`。

最终交付证据包含：实际基线与交付 HEAD、迁移验证、针对性测试、功能矩阵验收、最后一次仓库完整门禁及前端构建结果。提交、推送、上线仍遵循用户明确授权，本规划不执行这些动作。

## 14. 接入与回退

以增加可空字段、快照和新服务为主，旧表和旧记录保留。D1 建立副本数据库与只读数据统计基线，在副本验证升级、外键和旧记录数量；不在真实用户数据上试跑不可逆迁移。

先在测试环境验证四种组合，再切换正式页面的新建／续聊到统一写入。是否采用部署开关在实施时按需要决定，不预设长期双实现同步。切换期间同一记录只有一个写入口。

回退目标是停止新统一入口并保留已生成的 Task、事件和记忆事实，不倒灌旧 thread、不降级删除新字段、不自动重跑中断任务。运行中执行先按既有取消／停服协议结束并保留收据。新 schema 不保证旧二进制可直接运行，候选版本需明确验证代码回退兼容范围，不能只写“回滚代码即可”。

## 15. 实施前仍需核定的事项

这些事项有建议默认值，可在 P0 验证后定稿，不需要现在中断规划：

1. 已有未分域专家记忆的接入方式：建议保留原库，显式使用或整理来源，不自动升为通用记忆。
2. 专家文件人设的权威来源和完整配置版本：建议保留实际文件内容读取，并记录 digest，逐步统一编辑入口。
3. 记忆写入的目标端原子去重能力：若缺失，需要依赖库支持或明确降级为待核对写入，不能声称 exactly-once。
4. 共享专家和本地团队是否是首批必须替换的入口：本计划列入 M3，未通过专项验收则保留原入口。
5. 实际人力、启动日与高级工具的必需清单：目前日期按双工程师并行估算；资源变化后重新排期。
