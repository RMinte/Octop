# 项目和任务增量同步设计草案

状态：已接入服务端和网页；任务详情协议另行设计。日期：2026 年 10 月 15 日。

项目和任务分开同步。项目数量通常较少，首次可以获取完整项目列表；任务数量可能很多，首次只获取当前列表的一页摘要，后续按需翻页，不以下载全部任务作为可用条件。任务详情单独设计，不跟随列表下发。

客户端保存本地数据、分页位置和增量同步位置。分页用于获取尚未加载的任务，增量同步用于接收后续变化。同一对象多次变化，服务端合并后只返回本批截止版本的最终状态。

## 已确认的原则

| 事项 | 已确认的方向 |
| --- | --- |
| 项目和任务的游标 | 各自独立，不共用一个同步游标 |
| 任务的数据层次 | 区分任务列表和任务详情，本方案先处理列表 |
| 任务首次加载 | 使用游标分页，只获取一页，继续浏览时再取下一页 |
| 多次修改的返回方式 | 合并为对象的最终状态，不回放每次操作 |
| 首版范围 | 项目配置和任务摘要，详情与回复正文另行设计 |

变过的对象返回完整同步字段，首版不计算字段级补丁。只改项目名称时，返回该项目完整配置，其他项目不重发。服务端保存持久化变更记录定位变化，无需为每次修改保存所有项目和任务的完整快照。

这会减少传输、解析和列表重建的开销。网络往返延迟仍然存在；已有本地数据时先展示缓存，再同步更新，才能减少用户打开页面时的等待。

## 当前接口和数据范围

项目基础列表返回完整 `ProjectView[]`，包含目录、指南、Skill/MCP 引用和项目版本；同步入口返回独立项目快照或增量。任务列表返回分页摘要对象，页面约每 30 秒同步所在列表。选中会话按需分页，并通过多任务共享的 WebSocket 获取可续接的轮次最新状态；发送、停止和重试也走该连接，执行仍串行。项目和任务统一通过标准 API 调用独立项目和多轮任务服务。

| 数据 | 本方案中的处理方式 |
| --- | --- |
| 项目配置 | 首次获取完整列表，之后按项目同步游标获取变化 |
| 任务摘要 | 按当前列表分页获取，之后使用独立的任务同步游标获取变化 |
| 任务详情 | 打开具体任务时读取；历史、正文和执行细节的增量协议另行设计 |
| 删除记录 | 按 ID 移除本地对象，任务保存删除版本以拦截迟到的旧响应 |

任务摘要包含 archived 状态，分页入口按 archived=false/true 分别加载未归档/归档任务。归档保留任务及对话，恢复后可继续。项目仍独立于专家，任务仍是可继续的多轮会话，包含无项目任务。客户端工作目录只同步路径字符串，不探测、读取或上传目录文件。删除项目会连同其中全部任务一起删除；任务也可单独删除，均保留工作目录文件。项目同样支持独立归档和恢复，不修改任务各自的归档状态；归档前须停止全部运行任务，归档后保留历史，恢复前不能执行新的任务轮次。

## 三种游标分别表示什么

| 名称 | 用途 | 不能用来表示什么 |
| --- | --- | --- |
| 项目 `sync_cursor` | 项目列表的变化已经同步到哪里 | 不表示任务的同步进度 |
| 任务 `page_cursor` | 当前任务列表下一页从哪个排序位置继续 | 不表示已经接收了之后发生的变化 |
| 任务 `sync_cursor` | 任务列表从建立基线起发生的变化，已经处理到哪里 | 不表示历史任务已经全部下载 |

项目列表同步全部项目（含归档项目），网页依据 `archived` 显示未归档或归档列表，保留最新版本以防旧响应覆盖归档状态。项目 `revision` 继续表示单个项目的编辑版本，用于 `expected_revision` 冲突检查，与同步游标分别使用。项目 ID 和任务 ID 是稳定身份，修改后不变。

任务状态按列表分别保存：每个项目的任务列表各有自己的分页位置、同步位置和已加载范围，无项目任务列表单独保存。客户端只在进入相应列表时建立它的状态，不要求先下载其他项目的任务。

所有游标都作为不透明字符串原样保存和传回。服务端将它们绑定到实例、用户、协议版本、数据恢复代次和列表范围；任务历史分页游标额外绑定排序规则。其他账号、其他项目、其他用途的游标不能混用。

现有 `boxID`、`restoreEpoch` 可作为实例和恢复代次的接入依据，但实际恢复流程必须可靠地更新代次，使备份恢复前的游标失效。

## 项目列表如何同步

### 首次获取

客户端没有项目缓存时，读取本人的全部项目配置，并在同一读视图中获取项目同步位置。返回 `mode=snapshot`、完整项目集合和 `next_sync_cursor`。项目缓存建立后即可展示，无需等待任务数据。

重新建立项目快照时，用完整结果替换旧项目缓存，避免已删除的项目残留。已有业务数据直接进入快照，不重新创建项目，也不补造过去每次修改的记录。

### 后续更新

客户端携带项目 `sync_cursor`，服务端返回该位置之后发生过变化的项目。新增和修改使用 `upsert`，返回完整 `ProjectView`；删除使用 `delete`，返回项目 ID 和 `data=null`。

同一个项目连续改十次，本批最多返回一条最终状态。没有变化时返回空集合和有效同步位置。项目缓存与新的同步位置一起保存，失败时使用原位置重试。

## 任务首次只加载一页

### 打开列表

例如某项目有 10 万个任务。用户第一次进入时，服务端只查询最近一页摘要，例如 50 条，并返回以下信息。

| 返回内容 | 作用 |
| --- | --- |
| `items` | 当前页的任务摘要，不包含对话正文 |
| `next_page_cursor` | 继续浏览更早任务的位置，没有下一页则为 null |
| `sync_cursor` | 本列表首次建立时的变更基线，可立即用于后续增量同步 |

首屏拿到这一页就能展示，另外 99,950 个任务不用下载，也不要求服务端先扫描、复制或物化全部任务来生成分页游标。服务端按用户、所属项目和排序建立索引，用限制条数的查询读取一页及判断是否还有下一页；首版不要求计算任务总数。

第一页和同步基线必须来自同一个数据库读快照，避免第一页读取期间发生的变化落在两者之间而丢失。同步基线的含义是“接下来从这里接收变化”，不是“这里之前的任务已经全部缓存”。空列表也应返回基线，以便接收后续创建。

### 继续浏览

用户向下滚动或点击下一页时，传回 `page_cursor`，再读取一页摘要。没有继续浏览，就不加载后面的任务。只有 `next_page_cursor=null` 才表示按这次分页过程已经浏览到末尾，不能把第一页误当作完整任务集合。

沿用现有规则排序：`updated_at DESC, task_id DESC`。分页游标保存最后一项的排序位置，下一页从该位置之后继续查询；相同更新时间由任务 ID 确定顺序。首版使用基于位置的游标分页，避免用越翻越大的偏移量扫描历史。

后续分页只推进浏览位置，不能直接推进增量同步位置。即使第二页读到了很新的数据，也不代表客户端已经处理了期间所有新增、更新和删除。

### 列表在翻页时发生变化

任务列表按最新活动排序，翻页期间旧任务可能收到追问并移到顶部。历史分页使用实时数据视图，不承诺跨多页冻结整个任务列表；新建或移到顶部的任务由增量同步补充，重复出现的任务按 ID 合并。

例如第一页在变更位置 100 建立基线。一个尚未加载的旧任务随后在 101 更新并移到顶部，即使后续历史分页不再遇到它，增量同步也会返回它的最新摘要。没有变化的历史任务仍留待按需翻页，不因建立同步位置而被全量下发。

分页响应和增量响应可能交错到达。任务摘要使用单调递增的 `list_revision`，仅在列表字段变化时递增；分页项和增量项都携带它。客户端只应用更高版本，同版本重复应用保持幂等，旧分页结果不能覆盖已经收到的新摘要。

删除记录也携带对应任务的更高摘要版本，本地保留该删除版本，避免迟到的旧分页响应把任务重新加回来。重建列表缓存时，再统一重建版本和分页状态。

## 任务列表如何接收增量

第一页成功后就可以使用任务 `sync_cursor` 同步，不必等到全部历史分页完成。同步只覆盖当前列表，从该基线之后读取变更记录，并合并同一任务的多次变化。

| 变化 | 客户端处理 |
| --- | --- |
| 新任务 | 加入本地列表并按最新活动排序 |
| 已缓存任务的摘要变化 | 按 ID 和摘要版本更新，再调整排序 |
| 尚未加载的旧任务发生变化 | 返回它的最新摘要，加入近期活动位置 |
| 删除任务 | 移除对应任务并保留删除版本；未缓存过也可处理 |
| 没有变化 | 保留已有列表，不补发未加载的历史任务 |

一个很早创建且一直没变化的任务，不会因为客户端携带较新的同步游标而自动下发。它仍然通过历史分页按需获取。这允许本地长期保持“已加载部分列表，并已处理这些基线之后的变化”，无需拥有全部历史任务。

当前 `TaskSummary` 包含所属项目、标题、归档标记、任务 `status`、活动轮次和时间。`status` 由服务端持久维护，取值为 `queued`、`running`、`completed`、`failed`、`cancelled`，表示当前或最近一轮的执行状态。首条消息和追问进入 `queued`，worker 领取后进入 `running`，结束后更新为对应结果。每次状态变化与 `list_revision` 递增、增量记录在同一事务内提交；取消以实际保存的终态为准。

每页直接批量返回所有任务的 `status`，加载一页只需一次列表请求。客户端直接使用列表缓存绘制侧栏，后续通过现有列表增量更新状态；打开某个任务才读取正文详情，不逐个读取任务详情补状态。改名、归档和恢复同样更新摘要版本并生成变更。正文、工具活动、用量或心跳变化不进入此同步流。

一次增量可能有很多变化，仍需分页。服务端固定本批截止版本，按对象合并最终状态并使用稳定顺序分页；内容必须来自截止版本对应的记录，不能混入截止之后的当前状态。中间页返回 `next_page_cursor`，最后一页才给出可提交的 `next_sync_cursor`。

这里的增量 `next_page_cursor` 仅用于续取本批变更，与历史列表的 `next_page_cursor` 分开保存，服务端校验两者用途。客户端收齐本批后，原子地应用变更和推进同步位置；中断时从原同步位置重试。增量重试不会触发全部历史任务下载。

## 接口草案

以下路径和字段已接入标准项目/任务接口，暂不提供 AgentComputer 专用协议或 Bridge 转发。现有任务列表响应由数组改为分页对象，调用方需要适配；不引入旧专家绑定模型兼容。

| 用途 | 接口 |
| --- | --- |
| 项目初始快照或增量 | `GET /api/projects/sync` |
| 项目内任务分页 | `GET /api/projects/{project_id}/tasks` |
| 项目内任务增量 | `GET /api/projects/{project_id}/tasks/sync` |
| 无项目任务分页 | `GET /api/project-tasks` |
| 无项目任务增量 | `GET /api/project-tasks/sync` |

任务列表和增量都接受 archived=false/true，默认 false。两种视图的游标和网页缓存独立；共用项目内的持久变更记录，但不能跨视图传递游标。增量返回变过任务的最新摘要，包括移出当前筛选的任务；客户端按 archived 更新显示，并保留较高摘要版本，避免迟到页复活旧状态。历史分页请求传 `limit` 和可选 `page_cursor`；默认 `limit=50`，上限为 100。增量请求传 `sync_cursor`，分页续取再携带服务端返回的本批分页游标。项目同步不带 `sync_cursor` 表示获取项目完整快照；任务增量入口必须携带同步基线，首次列表使用分页入口建立基线。

任务第一页响应示例：

```json
{
  "items": [
    {
      "task_id": "task_example",
      "project_id": "proj_example",
      "title": "整理项目需求",
      "archived": false,
      "status": "queued",
      "active_turn_id": "turn_example",
      "list_revision": 1,
      "created_at": "2026-10-15T02:01:00Z",
      "updated_at": "2026-10-15T02:01:00Z"
    }
  ],
  "next_page_cursor": "task_history_example",
  "sync_cursor": "task_sync_example_100"
}
```

`items` 的基础字段复用现有任务摘要，`list_revision` 为任务列表版本。后续历史分页不提供可推进同步位置的新基线，`sync_cursor` 返回 null；增量位置由同步接口独立推进。

任务列表一次完整增量响应示例：

```json
{
  "base_sync_cursor": "task_sync_example_100",
  "next_sync_cursor": "task_sync_example_102",
  "next_page_cursor": null,
  "changes": [
    {
      "operation": "upsert",
      "task_id": "task_example",
      "list_revision": 3,
      "data": {
        "task_id": "task_example",
        "project_id": "proj_example",
        "title": "整理项目需求",
        "archived": false,
        "status": "completed",
        "active_turn_id": null,
        "list_revision": 3,
        "created_at": "2026-10-15T02:01:00Z",
        "updated_at": "2026-10-15T02:03:00Z"
      }
    }
  ]
}
```

`upsert.data` 返回完整摘要，外层 ID、版本与正文中的相应字段一致。`delete` 返回 `operation`、`task_id`、`list_revision` 和 `data=null`。中间页的 `next_sync_cursor=null`，最后一页才返回可保存的同步位置。无变化时 `changes=[]`，同时返回有效的同步位置。

项目增量使用相同的最终状态合并原则，返回对象改为项目，并保留现有项目 `revision`。两个同步入口分别管理各自的游标与变更记录。

## 失效和重新加载

同步游标将变更序号按需编码为 1 至 8 字节，附加 8 字节 HMAC-SHA256 校验值，整体采用无填充 Base64URL 编码。32 位以内的同步位置得到 12 至 16 个 URL 安全字符，超过后按需增长以避免溢出。服务实例、恢复代次、用户、列表范围和游标用途参与签名校验，不放进 URL。历史与增量分页游标只携带各自需要的时间、序号和对象 ID，同样签名；服务端不保存游标映射表。客户端将游标作为不透明字符串原样传回，不解析其内部格式。

当前变更历史不自动清理，保留期限待确定。游标签名、作用域、协议或恢复代次不匹配，以及同步位置超出当前范围时，服务端返回 HTTP 409 `PROJECT_SYNC_RESET`。后续增加历史清理时，应同时维护最早有效位置。

任务状态字段上线时变更任务列表游标和网页任务缓存版本，旧游标需重建第一页，避免沿用不含 `status` 的旧摘要记录。已有任务从活动轮次或最近一轮初始化状态，保留任务、轮次、正文和历史增量记录；不补造过去的状态变更。

| 失效范围 | 恢复方式 |
| --- | --- |
| 项目同步位置失效 | 重取当前用户完整项目列表并建立新基线 |
| 某个任务列表同步位置失效 | 重建该列表的第一页、历史分页位置和同步基线；旧缓存不再作为有效范围合并 |
| 历史分页游标失效 | 清除该列表的浏览位置，重新从第一页建立浏览范围 |
| 增量批次分页失效 | 丢弃未完成批次，从原同步位置重试；原位置也失效时重建第一页 |

任务重新建立基线仍然只需要第一页，不要求重新同步全部历史任务。尚未重新获取的旧缓存可以被淘汰，但这仅影响客户端缓存，不删除服务端项目、任务或对话。认证失败按原认证流程处理，不伪装成空列表。

## 服务端和客户端必须保证的规则

业务数据、变更记录、对应作用域序列推进和任务摘要版本必须在同一个数据库事务里提交。标准 API 和后台任务执行都走这套规则；失败请求和幂等重放不重复生成业务变更。

项目序列与任务列表序列分别管理。同一作用域的序列按可见提交顺序推进，事务内锁定对应序列并持锁到提交。不能直接用生成时间、ULID 或普通自增主键代表已提交同步位置，避免较大序号先提交后跳过尚未提交的较小序号。

后续查询按作用域和序列定位变更，分页查询按列表排序索引读取。第一页只读取有限摘要和当前序列，不预生成全任务快照。已有任务可以建立初始摘要版本，不需要补造历史变更，也不修改已有会话内容。

清理同步历史必须同步推进最早有效位置，并保证有效期内的增量分页有可用记录；记录不可用时明确使游标失效。清理只针对辅助记录，不删除业务历史。删除任务需要保留删除版本和记录供客户端同步。

客户端缓存按服务地址、用户和列表范围隔离；游标在服务端校验实例和恢复代次，每个列表分别保存已加载范围、历史分页位置、同步位置和摘要版本。响应按 ID 去重并校验版本，增量对象与同步位置一起保存；项目和各任务列表的同步可独立推进。

本地新建或修改成功时，可以先用写入响应更新显示，再同步补齐其他设备的变化。写入响应中用于更新任务摘要缓存的部分，也必须携带当前 `list_revision`。不能把本次写入的最新变更 ID 直接当作已同步位置，否则可能跳过期间其他写入。摘要版本检查也应覆盖写入响应和增量响应的交错。

任务摘要变更只使相应列表更新，不自动重取所有任务详情。打开具体任务时再读取详情，历史轮次分页和可续接轮次状态订阅使用任务详情接口及 `/events`，与列表游标独立，详见 [API 说明](api.md#实时状态续接)。

## 实现后的验收场景

| 场景 | 应得到的结果 |
| --- | --- |
| 用户有少量项目和 10 万个历史任务 | 项目独立加载，任务首屏只查询并返回一页摘要，不生成全任务快照 |
| 用户不继续浏览 | 不下载剩余历史任务，也不阻塞增量同步 |
| 项目列表更新，任务列表没有变化 | 仅项目同步位置推进，任务不被重发 |
| 首次列表为空后创建任务 | 用空列表返回的基线收到新摘要 |
| 第一页与建立基线期间发生写入 | 通过一致读视图和后续增量覆盖，不遗漏变化 |
| 连续翻页或多条任务时间相同 | 用排序位置和 ID 稳定续取，重复项按 ID 合并 |
| 尚未加载的旧任务更新并移到顶部 | 增量返回它的新摘要，不依赖历史页再次遇到它 |
| 同步后旧分页响应才到达 | 旧摘要版本不覆盖新数据，删除标记不被旧页复活 |
| 任务连续修改多次或后台结束 | 增量仅返回最终摘要一次，详情正文不进入列表 |
| 增量响应丢失或中途断网 | 使用原同步位置重试，重复应用不新增重复任务 |
| 任务同步位置过期或服务端恢复备份 | 重建对应任务第一页，无需下载全部历史任务 |
| 后续历史分页返回当前数据 | 只推进浏览位置，不越过未处理的增量变化 |

## 当前实现取值

| 事项 | 当前实现 |
| --- | --- |
| 任务列表范围 | 按项目分别管理，无项目任务单独管理 |
| 每页数量 | 默认 50 条，最多 100 条 |
| 翻页时的列表变化 | 实时位置分页配合增量补齐，按摘要版本解决响应交错 |
| 历史保留期限 | 暂不自动清理，确定期限后再实现清理与过期边界 |
| 网页缓存 | 按服务地址、账号和列表保存到 sessionStorage，不缓存任务对话正文 |
| 入口范围 | 标准项目/任务 API；不提供专用协议或 Bridge 转发 |

## 当前实现依据

- [现有 API 说明](api.md)：标准项目/任务入口、项目字段、任务语义和实时状态续接方式。
- `src/octop/api/routers/projects.py`：当前完整项目列表、分项目任务列表、无项目任务列表和详情入口。
- `src/octop/infra/projects/service.py`：项目创建幂等和版本冲突检查。
- `src/octop/infra/projects/tasks.py`：任务摘要与会话详情边界。
- `src/octop/infra/projects/runtime.py`：后台执行、结束和中断恢复对任务摘要的更新。
- `dashboard/src/pages/BoxProjects/TaskConversations.tsx`：约每 30 秒同步任务列表；`useTaskConversation.ts` 管理会话分页和实时续接。

任务协议 v3 的 waiting_approval、waiting_answer、waiting_client_tool、paused 同样通过 list_revision 进入列表增量同步，均保留 active_turn_id。具体交互规则见[审批、提问和暂停恢复](project-task-interactions.md)。

任务摘要还包含 approval_policy={mode,revision,updated_at}。切换模式递增 list_revision 并写入列表增量；模式按独立 approval_policy.revision 合并，迟到历史页和普通轮次事件不得覆盖更新的模式。浏览器任务列表缓存升为 3，旧缓存失效后重建。
