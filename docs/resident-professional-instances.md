# 统一生活工作管家与专业工作委派

用户面对一位长期的生活工作管家，负责理解需求、整理安排、持续交流和跟进结果。每个用户沿用唯一 `primary` 绑定及其 `agent_id`、`thread_id` 和私人记忆；处理不同领域的问题时继续使用同一管家身份。

## 管家、专家、会话、项目和任务

| 对象 | 职责 |
| --- | --- |
| 管家 | 统一承接生活与工作需求，保存持续关系和私人记忆，整理专业工作的目标与结果。 |
| 专家 | 既有专业方法与能力的来源。专业需求通过普通 Task 的配置与执行能力落实，不为用户建立一组独立专业助手。 |
| 会话 | 管家与用户持续交流的原 thread，汇合回答、任务回报和明确授权的跟进通知。 |
| 项目 | 独立保存工作目录、行动指南、Skill/MCP 等配置，由用户选择；不关联或创建专家。 |
| Task | 具体工作的独立执行会话，可有项目，也可无项目；沿用任务自己的能力、权限与审批。 |

当前委派入口创建普通 Task，不提供自动选择或绑定某个专家的路由。专业方法可由明确选择的任务配置提供，不复制专家的私人历史、记忆或凭据，也不修改专家。

## 一次专业工作的闭环

1. 用户在同一管家会话提出需求，管家澄清目标、交付要求和所需信息。
2. 管家根据工作请求判断是否需要独立执行，按需调用 `resident_create_task` 整理说明并创建一个普通 Task。客户端只需发送 `request_id/prompt`，不需要先创建任务或传 `task_context`；闲聊和咨询继续直接交流，信息不足先追问。
3. 默认创建无项目 Task，使用任务自己的独立工作空间，不附加客户端工具、附件、Skill、MCP、插件、子代理、知识库、长期记忆或团队授权。有特定项目、设备或附件需求时，可用 `task_context` 明确选择，模型不能从历史猜测。实际执行沿用普通 Task 的权限与审批规则，独立工作空间不等于操作系统沙箱。
4. Task 的真实终态及成果引用通过持久回报返回原管家会话。后续追问沿用这个会话，可结合结果继续整理和决定下一步。
5. 需要持续关注或定时工作时，另行创建明确的跟进授权；任务回报本身不会触发新委派或自动沉淀长期记忆。

每轮只有一个任务槽，与是否提供 `task_context` 无关；同一工作说明的重复工具调用复用原 Task，不因重试创建第二份。`task_context` 是可选高级范围，模型不能替换用户选定的项目、设备或权限。独立委派接口、自然语言验收、幂等身份和可靠回流见[任务委派与成果回流](resident-delegation-results.md)，按轮选择字段见[能力与接入顺序](resident-server-capabilities.md)。

## 原专业实例设计已撤下

此前创建多个私人专业实例、切换专业会话和采用专家模板的设计已撤下，`/api/agents/resident-profiles` 及其子路由不再提供，也不作为客户端接入入口。服务端自动准备唯一管家，客户端读取绑定后直接发送需求，再展示任务关联与回流。

既有专业实例记录、身份、历史和记忆保持原样，不迁移、不合并、不删除；它们不会自动成为管家的新身份或专业工作委派对象。此次调整不改动 AgentComputer 客户端。
